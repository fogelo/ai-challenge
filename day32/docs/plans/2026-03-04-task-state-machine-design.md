# Task State Machine - Design Document

**Дата:** 2026-03-04
**Автор:** AI Challenge Day 13
**Цель:** Реализация конечного автомата состояний задачи для создания stateful агента

## Проблема

Текущий агент является stateless — он не отслеживает формализованное состояние выполнения задач. Это приводит к:
- Отсутствию структурированного workflow (планирование → выполнение → проверка)
- Невозможности корректно продолжить задачу после паузы
- Агент может "перепрыгивать" этапы или повторять уже выполненные действия

## Решение

Реализовать Task State Machine — конечный автомат с четкими состояниями и разрешенными переходами:
- **PLANNING** → **EXECUTION** → **VALIDATION** → **DONE**

## Архитектура

### 1. Состояния (TaskState)

```typescript
enum TaskState {
  PLANNING = 'planning',       // Планирование задачи
  EXECUTION = 'execution',     // Выполнение плана
  VALIDATION = 'validation',   // Проверка результата
  DONE = 'done'                // Завершение
}
```

### 2. Контекст задачи (TaskContext)

```typescript
interface TaskContext {
  taskId: string;              // Уникальный ID
  description: string;         // Описание задачи
  currentState: TaskState;     // Текущее состояние
  startedAt: Date;             // Время создания
  updatedAt: Date;             // Время последнего обновления
  stateHistory: StateTransition[];  // История переходов
  planContent?: string;        // План (для PLANNING)
  executionResult?: string;    // Результат (для EXECUTION)
  validationResult?: string;   // Результат проверки (для VALIDATION)
}
```

### 3. Разрешенные переходы

```typescript
const ALLOWED_TRANSITIONS = {
  PLANNING: [EXECUTION],
  EXECUTION: [PLANNING, VALIDATION],
  VALIDATION: [EXECUTION, DONE],
  DONE: []
}
```

**Логика переходов:**
- PLANNING → EXECUTION: План утвержден, начинаем реализацию
- EXECUTION → PLANNING: Нужны изменения в плане
- EXECUTION → VALIDATION: Код готов к проверке
- VALIDATION → EXECUTION: Найдены проблемы, нужны доработки
- VALIDATION → DONE: Все работает, задача завершена

### 4. Структура модуля

```
src/taskstate/
  ├── types.ts              # Типы, enum, интерфейсы
  ├── TaskStateMachine.ts   # Класс автомата
  └── index.ts              # Экспорты
```

## Ключевые компоненты

### TaskStateMachine класс

**Методы:**
- `createTask(description)` - создать новую задачу в состоянии PLANNING
- `transition(nextState, reason?)` - попытка перехода (с валидацией)
- `save()` - сохранить состояние в файл
- `load(taskId)` - загрузить состояние из файла
- `getCurrentState()` - получить текущий контекст
- `getStatePrompt()` - получить промпт-инжекцию для LLM
- `listTasks()` - список всех задач

**Персистентность:**
- Файлы хранятся в `.task-state/<taskId>.json`
- Формат: JSON с полным TaskContext
- Автосохранение после каждого изменения

## Промпт-инжекция

Пример блока, добавляемого в системный промпт:

```
=== ТЕКУЩЕЕ СОСТОЯНИЕ ЗАДАЧИ ===
Задача: Написать REST API для управления задачами
Текущий этап: PLANNING
Что делать: Задай уточняющие вопросы пользователю, составь детальный план.
            НЕ начинай выполнение до утверждения плана.
История переходов: START → PLANNING
===
```

## Поведение агента

### PLANNING (Планирование)
- Задает уточняющие вопросы
- Формирует детальный план
- Ждет утверждения от пользователя
- НЕ начинает выполнение

### EXECUTION (Выполнение)
- Реализует утвержденный план
- Придерживается плана
- Не делает лишних изменений
- Сообщает о завершении

### VALIDATION (Проверка)
- Проверяет результат
- Предлагает тесты
- Ищет проблемы
- Рекомендует улучшения

### DONE (Завершено)
- Подводит итоги
- Показывает результат
- Задача закрыта

## Автоматические переходы

Система анализирует ответы пользователя и определяет намерение перейти:
- "утверждаю план" / "да, начинай" → PLANNING → EXECUTION
- "проверь" / "готово" → EXECUTION → VALIDATION
- "все работает" / "отлично" → VALIDATION → DONE

Также доступен явный переход через `/next`.

## Требования к реализации

✅ Формализованное состояние задачи (enum + контекст)
✅ Разрешенные переходы с валидацией
✅ Персистентность (пауза/восстановление)
✅ Промпт-инжекция для каждого состояния
✅ Визуальные индикаторы
✅ Команды управления (/task, /next)
✅ История переходов
✅ Отсутствие повторных вопросов при восстановлении

## Trade-offs

**Выбранный подход: Промпт-инжекция + валидация переходов**

✅ Плюсы:
- Простота реализации
- Легкая интеграция с текущей архитектурой
- Состояние персистентно через JSON
- Гибкость для LLM

⚠️ Минусы:
- LLM может игнорировать инструкции (решается валидацией)
- Требует тестирования на разных промптах

**Альтернатива (не выбрана): Полная изоляция состояний**
- Каждое состояние = отдельная сессия LLM
- Максимальная детерминированность
- Избыточно сложно для учебного проекта

## Метрики успеха

1. ✅ Агент проходит все 4 состояния последовательно
2. ✅ Паузу можно сделать на любом этапе
3. ✅ Восстановление продолжает с того же состояния
4. ✅ Нет повторных вопросов при восстановлении
5. ✅ Недопустимые переходы блокируются
