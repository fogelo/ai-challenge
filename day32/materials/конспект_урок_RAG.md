# Конспект урока: RAG (Retrieval Augmented Generation)

## 1. Что такое RAG

**RAG (Retrieval Augmented Generation)** — паттерн дополнения ответов LLM с помощью внешних знаний во время инференса.

- Модель отвечает не только из общей базы знаний (полученной при обучении), но и из специфических внутренних данных
- **Отличие от MCP:** MCP — общение с внешними источниками данных, RAG — работа с внутренними знаниями
- Данные подгружаются прямо во время инференса, а не через внешний инструмент

---

## 2. Проблемы без RAG

| Проблема | Описание |
|---|---|
| Неполный контекст | Модели обучены на общих данных (Wikipedia, Reddit, GitHub), не знают ваших специфических данных |
| Медленный поиск | Перелопатить весь Confluence в поисках нужного занимает очень долго |
| Устаревшие/дублирующиеся данные | Нейронка не может отличить актуальную версию от старой |
| Галлюцинации | Модель даёт ответ, похожий на правду, но неверный — это опаснее, чем очевидно неправильный ответ |

---

## 3. Способы улучшения LLM

```
┌──────────────────────────────────────────┐
│         Способы улучшения LLM            │
├─────────────────────┬────────────────────┤
│ Контекст-оптимизация│  LLM-оптимизация   │
│ (что модель знает)  │ (как модель думает)│
├─────────────────────┼────────────────────┤
│ • Промпт-инжиниринг │ • Fine-tuning      │
│ • RAG               │   (изменение весов)│
└─────────────────────┴────────────────────┘
```

**Важно:** RAG и Fine-tuning — аддитивные, не эксклюзивные методы. В реальных системах используются вместе.

### Пример: без RAG vs с RAG

**Без RAG:** «Код-ревью обычно требует одного апрувала и должен быть сделан в течение недели» *(галлюцинация — среднее по рынку)*

**С RAG:** «Согласно [ссылка на Confluence/GitHub], код-ревью требует минимум 2 апрувала, максимальное время ревью — 24 часа» *(источник указан)*

---

## 4. Как работает RAG — общая схема

```
Запрос пользователя
       ↓
Определение пробелов в знаниях модели
       ↓
Запрос к векторной базе данных (RAG)
       ↓
Получение релевантных чанков
       ↓
Комбинирование чанков с промптом
       ↓
Ответ LLM с источниками
```

## 5. Embedding-модели

### Зачем нужны
- **Генеративные модели** (GPT и др.) — генерируют текст
- **Embedding-модели** — кодируют текст в числовой вектор для поиска семантических связей

### Как работает сравнение векторов (косинусное сходство)

| Значение | Смысл |
|---|---|
| `= 1` | Тексты близки по смыслу |
| `= 0` | Тексты о разном (не пересекаются) |
| `= -1` | Тексты противоположны по смыслу |

### Процесс векторизации текста

```
Входной текст → Токенизация → Embedding Layer → Self-Attention → Pooling → Вектор предложения
```

1. **Токенизация** — разбивка на токены
2. **Embedding layer** — каждому токену свой вектор
3. **Self-attention** — определение взаимосвязи слов внутри предложения
4. **Pooling** — усреднение векторов → итоговый вектор предложения

### Параметры моделей

- Размерность: **768**, **1024**, **3072** и др.
- Чем больше размерность — тем выше точность (как у хэш-функции: больше бит → меньше коллизий)
- Есть специализированные модели под конкретные языки

### Популярная модель: Ollama (nomic-embed-text и др.)
- Локальная — данные не покидают компьютер
- Бесплатная
- Совместима с облачными эмбеддерами
- Подходит для прототипирования

## 6. Chunking (нарезка текста)

Перед векторизацией текст нарезается на **чанки** — фрагменты для хранения в БД.

### Способы нарезки

| Метод | Описание | Недостаток |
|---|---|---|
| **Фиксированный** | Каждые N токенов (напр. 500) | Может разрезать предложение пополам |
| **Семантический** | По блокам/абзацам | Сложнее реализовать |
| **С перекрытием (Overlap)** | 0-500, 450-950, 900-1400... | — |

### Overlap (перекрытие) — рекомендуемый подход
- Чанки частично перекрываются → граница «на замке»
- Размер чанка и overlap нужно подбирать экспериментально под каждую задачу

**Рекомендуемый размер чанка:** 500–1000 токенов

---

## 7. Reranking (переранжирование)

**Проблема:** Вектор-поиск может вернуть много похожих, но не точных результатов.

**Решение — Reranking:**
1. Получить топ-20 чанков по вектору
2. Прогнать через **cross-encoder модель** для более точного сравнения с запросом
3. Получить отсортированный список → передать в LLM

**Минус:** Замедляет пайплайн (миллисекунды–секунды), но повышает точность.

---

## 8. Нормализация векторов

Приведение всех значений вектора к диапазону **[0, 1]**:
```
нормализованное_значение = значение / максимальное_значение_в_векторе
```

---

## 9. Метрики качества RAG

| Метрика | Как замерять |
|---|---|
| **Релевантность чанков** | Палец вверх/вниз (как в ChatGPT) |
| **Правдивость ответов** | Процент ответов с источниками из базы vs из «головы» |
| **Точность финального ответа** | Сравнение с эталонными ответами (можно автоматизировать другой моделью) |

---

## 10. Когда RAG НЕ поможет

| Ситуация | Что использовать вместо |
|---|---|
| Мало данных или данные плохого качества | Fine-tuning |
| Нужна сложная логика принятия решений | Prompt Engineering |
| Нужен определённый стиль ответов | Agents + Tooling |
| Устаревший/нестандартный формат данных | Multimodal RAG или предварительная оцифровка |

---

## 11. Области применения RAG

- **Корпоративные базы знаний** — чаты, Wiki, Confluence
- **Приватность** — локальная модель обогащает ответы без отправки данных наружу
- **Специализированные агенты** — медицина, физика, право
- **Анализ трендов** — работа с большими оцифрованными датасетами
- **Цифровой двойник** — переписки, звонки, заметки → персональный RAG

## 13. Критический разбор урока

> Здесь собраны технические неточности, упрощения и важные пробелы, которые стоит учитывать при изучении темы.

### 13.1. Фактические ошибки и неточности

**❌ Нормализация описана неправильно**

В уроке: *«берёшь максимальное число, делишь всё на него — получается от 0 до 1»*

Это **L∞-нормализация** — редкий и нестандартный метод. В эмбеддингах применяется **L2-нормализация** (нормирование по длине вектора):

```
v_norm = v / ||v||₂ = v / sqrt(sum(v_i²))
```

Именно после L2-нормализации косинусное сходство сводится к скалярному произведению, и именно так работают все современные embedding-библиотеки (sentence-transformers, OpenAI API и др.).

---

**❌ Ollama — не embedding-модель**

В уроке Ollama неявно подаётся как «лучшая embedding-модель». На самом деле:
- **Ollama** — это runtime-среда для запуска моделей локально (аналог Docker для LLM)
- Через Ollama запускаются embedding-модели: `nomic-embed-text`, `mxbai-embed-large`, `bge-m3` и др.
- Качество эмбеддингов определяет конкретная модель, а не Ollama

---

**❌ Косинусное сходство «равно единице» для похожих текстов**

Утверждение что сходство = 1 означает «похожие тексты» — верно только для идентичных предложений. На практике:
- Релевантные тексты дают значения **0.7–0.95**
- Порог релевантности подбирается экспериментально под каждую задачу
- «Равно 1» в реальных запросах практически не встречается

---

**❌ Pooling — не только среднее арифметическое**

Урок описывает pooling исключительно как «среднее векторов». Существуют три распространённых стратегии:

| Стратегия | Описание |
|---|---|
| **Mean pooling** | Среднее всех токен-векторов (упомянуто в уроке) |
| **CLS-token pooling** | Вектор специального `[CLS]`-токена — используется в BERT |
| **Max pooling** | Максимальное значение по каждому измерению |

Выбор стратегии влияет на качество — модели обучаются под конкретный вид pooling.

---

### 13.2. Опасные упрощения

**⚠️ RAG vs MCP противопоставление слишком грубое**

Урок рисует чёткую границу: «MCP — внешние данные, RAG — внутренние знания». На практике это пересекается: MCP-сервер может возвращать векторный поиск по внутренней базе, а RAG может работать с публичными данными. Разница скорее в **механизме** (семантический поиск vs инструментальный вызов), а не в «внешнее/внутреннее».

---

**⚠️ Описание «как определяются пробелы в знаниях» — магия**

В схеме пайплайна сказано: «нейронка изучает запрос и определяет пробелы». Это представляет процесс как интеллектуальный анализ, хотя в базовом RAG ничего подобного нет — промпт просто всегда отправляется в векторную БД. «Умное» определение пробелов — это отдельный паттерн **Agentic RAG**, который в уроке не разбирается.

---

**⚠️ «Размер больше — точность выше» — не всегда**

Аналогия с хэш-функцией интуитивно понятна, но вводит в заблуждение: более высокая размерность эмбеддинга не гарантирует лучшего качества поиска. Качество зависит от:
- Данных и языка, на которых обучена модель
- Метода обучения (contrastive learning, RLHF и др.)
- Соответствия домена (общая модель vs специализированная)

Например, `text-embedding-3-small` (1536 dim) от OpenAI на многих бенчмарках превосходит более «размерные» опенсорсные модели.

### 13.3. Важные темы, которые не упомянуты

**🔴 Векторные базы данных**

Урок не называет ни одной конкретной БД для хранения эмбеддингов, хотя это ключевая практическая часть:
- **Chroma** — самая простая для старта, in-memory/локальная
- **pgvector** — расширение PostgreSQL, если уже есть PG
- **Qdrant, Weaviate, Pinecute** — production-решения
- **FAISS** — библиотека Facebook для локального поиска

---

**🔴 Hybrid Search (гибридный поиск)**

Чисто векторный поиск плохо работает с точными совпадениями (имена, артикулы, даты). Современные системы комбинируют:
- **Dense retrieval** — векторный поиск по смыслу (что описано в уроке)
- **Sparse retrieval (BM25/TF-IDF)** — классический полнотекстовый поиск по словам

Это один из главных практических улучшений базового RAG, и его пропуск — существенный пробел.

---

**🔴 Query Rewriting / HyDE**

Запрос пользователя часто не совпадает семантически с тем, как написаны документы в базе. Техники:
- **Query Rewriting** — LLM перефразирует вопрос перед поиском
- **HyDE (Hypothetical Document Embeddings)** — LLM генерирует гипотетический ответ, его вектор используется для поиска вместо вектора вопроса

---

**🔴 Метаданные и фильтрация**

В уроке чанки — просто текст. На практике к каждому чанку прикрепляют метаданные: автор, дата, отдел, тип документа — и используют их для **предварительной фильтрации** перед векторным поиском. Это радикально ускоряет поиск и повышает точность.

---

**🔴 Оценка качества: фреймворк RAGAS**

Упомянутый в уроке подход «палец вверх/вниз» — ручной и не масштабируемый. Индустриальный стандарт — фреймворк **RAGAS**, который автоматически считает:
- **Faithfulness** — насколько ответ основан на чанках
- **Answer Relevancy** — насколько ответ соответствует вопросу
- **Context Recall / Precision** — насколько правильные чанки были найдены

---

### 13.4. Структурные замечания к подаче материала

| Замечание | Пояснение |
|---|---|
| Термин «РАГ/РАК/РАЦ» используется непоследовательно | В разговорной речи лектора название аббревиатуры постоянно меняется, что затрудняет восприятие у новичков |
| Fine-tuning описан поверхностно | Сказано «меняем веса» без объяснения LoRA, PEFT и других доступных методов |
| Пример с «собаками и баскетболом» как негативный сэмпл | Хороший пример для объяснения contrastive learning, но опущен контекст: негативные примеры бывают «лёгкими» и «жёсткими» (hard negatives), и качество обучения зависит именно от последних |
| Reranking показан как опциональное ускорение | На практике reranking — почти обязательный шаг в production-системах, а не «если хочется точнее» |

### 13.5. Итоговая оценка

**Что хорошо в уроке:**
- Даёт правильное интуитивное понимание зачем нужен RAG
- Объясняет косинусное сходство через геометрию — это удачный дидактический приём
- Честно говорит о границах применимости RAG
- Практическая направленность (задания с Ollama и reranking)

**Что стоит изучить самостоятельно после урока:**
1. L2-нормализация и почему она стандарт для эмбеддингов
2. Векторные БД: начать с **Chroma** или **pgvector**
3. Hybrid Search: совместить BM25 + векторный поиск
4. Фреймворк **RAGAS** для автоматической оценки качества
5. Паттерн **HyDE** для улучшения качества поиска
